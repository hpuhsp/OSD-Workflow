## Context

The repository is a file-based OSD workflow template. Its verifier already checks required artifacts and text markers, while OpenSpec remains the canonical specification lifecycle and Superpowers remains the delegated development method. The change crosses the manifest, artifact templates, verifier, agent contracts, documentation, and regression fixtures, so the implementation needs a shared contract rather than isolated checks.

## Goals / Non-Goals

**Goals:**

- Define one machine-readable contract for state, approval, task traceability, evidence, and archive results.
- Keep the verifier deterministic and prevent it from executing commands found in authored artifacts.
- Preserve a lightweight path and maintain an explicit migration path for existing v3 changes.
- Make native OpenSpec archival an evidenced integration point rather than an OSD reimplementation.

**Non-Goals:**

- Reimplementing OpenSpec commands or Superpowers planning, brainstorming, TDD, or review mechanics.
- Requiring the new artifacts for unchanged lite work unless project policy escalates it.
- Creating a second canonical project specification tree outside OpenSpec.

## Decisions

1. **Use JSON for machine contracts and Markdown for human context.** State, approvals, task metadata, verification evidence, and archive results need schema validation; proposals, designs, and review notes remain readable Markdown. A fully JSON-based workflow was rejected because it would make human review unnecessarily difficult.

2. **Use stable IDs for criteria and tasks.** `AC-*` and `T-*` identifiers provide a small, repository-independent join key across specifications, tasks, tests, handoffs, and delivery records. Inferring links from prose was rejected because it cannot reliably detect omissions.

3. **Validate evidence without executing authored commands.** The verifier checks structure, exit-code semantics, strategy steps, and coverage. An optional allowlisted runner may generate evidence from repository-defined commands. Executing arbitrary Markdown commands was rejected for safety and reproducibility.

4. **Prefer native OpenSpec archive results.** OSD records the command outcome and archived location, while OpenSpec owns specification merging and lifecycle semantics. Duplicating archive logic in OSD was rejected because it would create competing sources of truth.

5. **Support v3 as an explicit legacy mode.** Existing projects continue to receive useful validation during migration, but legacy verification emits a warning and cannot claim the new guarantees. A hard cutover was rejected because it would break existing workflow repositories.

## Risks / Trade-offs

- **More artifacts increase ceremony** → Keep the new gate limited to standard and strict modes and retain the lite path.
- **Structured evidence can still be forged** → Prefer evidence generated by an allowlisted runner and require CI verification where available.
- **Native CLI behavior can vary by version** → Store the command result and archived location, and validate the local CLI before archive.
- **Migration may leave mixed-version changes** → Report the mode and legacy warning explicitly instead of silently upgrading claims.

## Migration Plan

1. Upgrade the manifest and templates while retaining v3 parsing.
2. Add positive and negative fixtures for each new contract.
3. Convert active standard/strict changes to the new state, approval, task, and evidence artifacts.
4. Run repository tests, structural verification, and native OpenSpec validation.
5. Archive completed changes through the installed OpenSpec CLI and record the result.
6. Roll back by restoring the prior manifest/verifier only if the new verifier causes unacceptable compatibility failures; do not delete existing change artifacts.
